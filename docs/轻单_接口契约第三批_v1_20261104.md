## 1. 操作日志（audit_log）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | uuid | ✅ | 日志主键，全局唯一 |
| 时间 | datetime | ✅ | 服务端时间（UTC 存储，按租户时区展示） |
| 租户 id | uuid | ✅ | 平台侧操作可空（平台级） |
| 公司 id | uuid | 选填 | 单据/档案类操作必填 |
| 操作者类型 | enum | ✅ | `platform` 平台开发者 / `employee` 员工 / `ai` AI / `system` 系统任务 |
| 操作者 id | uuid | ✅ | 员工 id 或平台账号 id；`system` 用固定标识 |
| 凭证 id | uuid | 选填 | AI 调用时为 token id；人类会话可记 session id |
| 来源 | enum | ✅ | `web` / `cli` / `api` / `mcp` / `job` |
| 动作 | text | ✅ | `功能域.动作`，如 `sales.create`、`settlement.confirm` |
| 对象类型 | text | ✅ | 单据/档案/权限/Token/日志 等 |
| 对象 id | uuid | 选填 | 目标实体主键 |
| 变更摘要 | json | 选填 | 变更前/后关键字段；金额与成本字段按「看价」权限脱敏（D27） |
| 结果 | enum | ✅ | `success` / `fail` |
| 错误码 | text | 选填 | 失败时填 |
| 请求 id | text | ✅ | 透传 `X-Request-Id`，用于全链路关联 |
| IP / UA | text | 选填 | 来源设备信息 |
| 原因 | text | 条件必填 | 危险动作（删除 / 冲正 / 成本更正 / 结算确认 / 权限变更）与 AI 写操作必填 |
| 业务事务 id | text | 选填 | 与业务写入关联，便于对账 |

**规则**：
- **只追加**：不提供更新 / 删除接口；平台侧保留独立副本，租户删除任何数据都不影响日志。
- **失败也记**：审计写入独立追加，不随业务事务回滚；业务失败同样落一条 `fail`。
- **口径一致**：金额类字段按 D27「看价」权限脱敏；日志本身的查看也记日志。
- **覆盖清单**（默认，见 §5 开放项 1）：登录 / 登出 / 失败登录、权限与岗位变更、个人权限覆盖、API Token 增删改、全部写操作、导出、查看敏感金额、查看操作日志、AI 全量调用、平台运营后台全部操作。

## 2. API Token（机器身份）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | uuid | ✅ | |
| 租户 id | uuid | ✅ | |
| 绑定员工 id | uuid | ✅ | 含专门创建的服务账号员工 |
| 名称 | text | ✅ | 便于识别人 / Agent / 系统 |
| scope | json | ✅ | 功能域 × 动作子集（8 动作枚举见第一批 §1.2） |
| 有效期 | datetime | 选填 | 到期自动失效 |
| IP 白名单 | text[] | 选填 | 空 = 不限制 |
| 最后使用时间 | datetime | 选填 | 每次调用更新（异步，允许延迟） |
| 状态 | enum | ✅ | `active` / `revoked` / `expired` |
| 创建人 | uuid | ✅ | 员工 id |
| 撤销时间 | datetime | 选填 | |

**规则**：
- 明文只在创建时返回一次，服务端只存哈希；可随时撤销。
- **权限 = 绑定员工权限**（公司集合 + 岗位并集 + 个人覆盖），再取 scope 交集；**不能超越人**，不提供租户级「上帝 token」（见 §5 开放项 4）。
- **不放大（D52.1）**：token 创建时 scope 只能从创建人自己的授权里选，超出直接拒绝创建；生效权限每次请求现算（岗位/个人覆盖/公司集合变更立即生效，员工停用 token 立即作废），不缓存授权。
- **审批必须人类**：AI 不能审批自己发起的动作，也不能担任任何审批人（D52① 的补充）。
- **可追溯**：审计同时记录 token 创建人与 AI 操作者，可反查「谁把这套权限委托给了 AI」。
- 写操作必须携带 `reason`（意图说明），进操作日志。
- 每 token 限流；超限返回 429 与 `Retry-After`。

## 3. 通用 API 约定

| 项 | 约定 |
|---|---|
| 版本 | `/api/v1`（破坏性变更才升版本） |
| 认证 | 人类：会话 Cookie；机器：`Authorization: Bearer <token>` |
| 错误体 | `{ "code": "...", "message": "...", "details": {...}, "requestId": "..." }`，HTTP 状态码与 `code` 同时给 |
| 分页 | 游标：`?cursor=&limit=`，`limit` 默认 50、最大 200；返回 `nextCursor` |
| 幂等 | 写接口支持 `Idempotency-Key`，24h 内重复请求返回首次结果 |
| 并发 | 单据/批次写接口要求 `If-Match: <version>`，冲突返回 409 |
| 预检 | 全部写接口支持 `dryRun=true`：只校验不落库，返回将要发生的变更与错误 |
| 请求 id | 客户端可传 `X-Request-Id`，服务端透传并回写；缺省则生成 |
| 时间 | ISO 8601 带时区；金额 decimal 字符串（避免浮点误差） |
| 文档 | `GET /api/v1/openapi.json`（OpenAPI 3.1，唯一接口真源） |
| 审计 | 每个写接口、每次 AI 调用都必须产生操作日志（§1） |

## 4. CLI 与 MCP 映射

- **CLI**：`qingdan <功能域> <动作> [--json] [--dry-run] [--reason "..."]`；退出码约定 `0` 成功 / `2` 用法错误 / `3` 无权限 / `4` 校验失败 / `5` 并发冲突。
- **MCP Server**：每个工具与一个 REST 接口一对一，工具描述里声明所需 scope 与是否需要 `reason` / 审批；Agent 通过 MCP 看到的权限与 Web 完全一致。
- **共同约束**：CLI 与 MCP 都是薄客户端，**不得绕过服务端权限与审计**；同一动作三种入口的行为、错误码、日志字段必须一致。

- **来源**：契约第三批 §3「并发」（第 90 行，只说「单据/批次写接口要求 `If-Match: <version>`，冲突返回 409」）；契约第一批 §3.1–§3.4、§5–§9、第二批 §1–§3 的字段表**均无** `id` / `version` / `createdAt` / `updatedAt`；`docs/api/openapi.yaml` `IfMatch` 参数（第 1336–1342 行，`required: true`）、`ETag` 头（第 1382–1385 行）、各实体 `version`（如第 1983–1986、2085–2087、2284–2286、2366–2368 行）、428 提案（第 1468–1469 行）。
- **影响模块**：**全部单据模块** + `platform` 单据框架 + 数据库 schema + `web`/`cli`/`mcp`。
- **建议默认口径（🟡）**：所有单据/批次实体加 `version`（整数，从 1 起，每次成功写 +1，列表也返回）；`GET` 回 `ETag: "<version>"`（OpenAPI 3.1 里 `If-Match` 用强 ETag 串）；「更新已存在实体」的写接口一律强制 `If-Match`（complete / confirm / receipts / permissions，以及将来的 ship / cancel / 成本更正），「创建」类不要求；缺 `If-Match` 回 428 `PRECONDITION_REQUIRED`（与 CLI 退出码 4 并存）。
- **拍板**：Lead。

### 缺口 6｜幂等语义（`Idempotency-Key`）

- **缺什么**：作用域（租户级唯一还是员工级）、是否强制、**同一 key 不同请求体**返回什么、重放是否再记审计、与 `dryRun` 的关系、幂等窗口从何时起算。
- **来源**：契约第三批 §3「幂等」（第 89 行，只有一句「写接口支持 `Idempotency-Key`，24h 内重复请求返回首次结果」）；`docs/api/openapi.yaml` `Conflict` 把 `IDEMPOTENCY_CONFLICT` 定为 **409**（第 1449–1453 行）；`docs/api/cli.md` §2 把该码映射退出码 **5**（第 48 行）；**`docs/adr-0001-tech-stack.md` 第 230 行却写「hash 不一致 → 422」——同一事实三处不一致**。
- **影响模块**：`platform`（幂等存储/回放）、**全部写接口**、`cli` 重试编排、`mcp`、AI 调用（D52）。
- **建议默认口径（🟡）**：作用域 = `(租户 id, Idempotency-Key)`；**可选头，带了才生效**（与 ADR 一致）；同 key 同体 → 回放首次响应，**不新增业务审计**（只记一条 replay 标记，标记形态未定 + TODO）；同 key 不同体 → **409 `IDEMPOTENCY_CONFLICT`**（同时把 ADR 第 230 行的 422 更正为 409，消除三处不一致）。
- **拍板**：Lead（并同步修正 ADR 该行）。

### 缺口 7｜`dryRun` 的语义边界

- **缺什么**：① 预检**是否落审计**（D51 说「每一次操作都留日志」，预检算不算一次操作）；② `changes` 的具体形状；③ 校验失败时回 200 + `DryRunResult(valid=false)` 还是 422；④ 是否消耗幂等键、是否要求 `If-Match`。
- **来源**：契约第三批 §3「预检」（第 91 行，只有「只校验不落库，返回将要发生的变更与错误」）；`docs/api/openapi.yaml` `DryRunResult.changes` 描述「具体形状待 platform 冻结」（第 1592–1594 行）；`docs/api/cli.md` §6（第 234–243 行，列出 8 个支持 dryRun 的写命令）、§8-8（第 264 行，自认「契约未规定」）。
- **影响模块**：**全部写接口**、审计、`cli`/`mcp`、AI 预检（D52 卖点之一）。
- **建议默认口径（🟡）**：`dryRun` 成功与失败**都回 200 + `DryRunResult`**（`valid=false` 时 `errors[]` 非空，与 CLI §2「valid=false → 退出码 4」对齐）；`changes` 形状 = `[{operation: create|update|delete, entity, id, before, after}]`；`dryRun` **不消耗**幂等键、**不要求** `If-Match`；**是否记审计 → 见 §8 待拍板问题 3（建议记一条带 `dryRun: true` 标记的审计）**。
- **拍板**：**负责人**（审计那一条，涉及 D51 解释）+ Lead（其余）。

### 缺口 8｜认证与会话细节、发码与「注册/入企」端点缺失

- **缺什么**：① 会话 Cookie 名、有效期、续期策略、登出是否失效全部会话、**CSRF 防护**；② **「发送短信验证码」端点**——`login` 需要 `code`，但三批契约与骨架都没有发码接口；③ **注册 / 入企端点**（邀请码、手机号白名单、老板预建三合一，D1）——契约第一批 §2 只有企业/公司/员工**字段表**，骨架 `/auth` 只有 3 个操作；④ 一人多设备的会话管理。
- **来源**：契约第三批 §3「认证」（第 86 行，只有「人类：会话 Cookie；机器：Bearer」）、§2「明文只在创建时返回一次」（第 71 行）；`docs/api/openapi.yaml` `securitySchemes`（第 1305–1319 行，Cookie 名「待 platform 冻结」）、`/auth/login`（第 117 行）、`/auth/logout`（第 176 行）、`/auth/me`（第 206 行）；`docs/decisions.md` D1「注册入企三合一」（第 21 行）；`docs/module-platform.md` 验收标准第 1 条（第 31 行，要求登录闭环 + 入企三合一）；`docs/adr-0001-tech-stack.md` U6（第 350 行，短信服务商未定）。
- **影响模块**：`platform`（登录/入企，P0 第一个验收项）、`web`、`cli`、安全。
- **建议默认口径（🟡）**：Cookie 名 `qingdan_session`、HttpOnly + Secure + SameSite=Lax、闲置 7 天滑动续期、登出只失效当前会话；写接口加同源 `Origin`/`Referer` 校验（或双提交 CSRF token，**未定 + TODO**）；新增 `/auth/sms-code`（发码，限流 + 图形/频控，具体方案**未定 + TODO**）、`/auth/register`（注册 + 入企三合一校验）、`/companies/{id}/invite-code`（老板生成邀请码）三个端点，列入第三批增补。短信服务商按 ADR-0001 U6 **未定 + TODO**。
- **拍板**：**负责人**（发码/入企是否一期、服务商选型）+ Lead（端点形态与路径）。

### 缺口 9｜平台运营后台（手动计费 / 企业停用）的接口与审计归属

- **缺什么**：① 运营后台是否走同一个 `/api/v1`、是否共用同一套审计写入；② 端点清单（企业列表 / 设套餐与到期 / 停用启用 / 用量查看）；③ 平台开发者账号的身份与权限模型（独立体系，还是员工表加标记）；④ 平台操作的租户归属（`tenantId` 填目标租户还是空）。
- **来源**：契约第三批 §0（第 17 行，**声明**覆盖「平台运营后台的审计要求（手动计费、企业停用等）」）——但正文 §1–§4 **无任何**运营后台条款，仅 §1「租户 id」行提到平台侧（第 29 行）；`docs/decisions.md` D1「手动计费配置」（第 22 行）、D12「后台手动裁定停用 + 到期站内提示」（第 49 行）、D51「平台操作也进日志」（第 90 行）；`docs/module-platform.md` 范围含「平台运营后台」（第 15 行）。
- **影响模块**：`platform` 运营后台、审计、计费、登录拦截（D12）、平台侧权限模型。
- **建议默认口径（🟡）**：一期进同一 API，前缀 `/api/v1/admin/**`（独立 tag `admin`，**不进** MCP/CLI 默认工具表）；首期至少 3 个端点：企业列表、设套餐与到期、停用/启用；平台账号独立于员工表（`actorType = platform`）；平台操作的 `tenantId` 填**目标租户**，只有「新增租户」这类纯平台级操作才为空（与缺口 3 同一裁决）。
- **拍板**：**负责人**（运营后台是否一期同仓、平台账号模型）。

### 缺口 10｜「业务能力 → REST」覆盖面与资源路径 / tag 命名规则
