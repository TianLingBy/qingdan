> **契约依据**：`docs/轻单_接口契约第一批_v1_20261103.md`（已冻结）、`docs/轻单_接口契约第三批_v1_20261104.md`（🟡 草案）、`docs/api/openapi.yaml`（0.1.0-draft）。

## 1. 实体与字段清单

> 为落表需要，把「动作授权集」「授权行」这类**集合型属性**拆成子表（§1.4b、§1.5），它们不新增业务概念、只是同一实体的存储形态。清单外但验收标准绕不开的实体统一放 §1.11，**明确标注未获授权扩清单**。

| 是否老板 | 布尔 | 必填**？** | 老板 = **租户级**：全部公司数据 + 集团主数据，不受「绑定公司集合」限制；表达方式 ⬜（见下） | D1 / D15 |

**约束与坑**
- **「老板」怎么表达 ⬜（未定 + TODO）**：D1/D15 说「老板 = 租户级」，但 D4/F8 又把「老板」列为一套**出厂预设岗位**。两种表达会导致完全不同的判定代码：
  - 方案 A `是否老板` 布尔在员工上 → 判定时短路（跳过公司集合与动作集）；
  - 方案 B 老板 = 岗位，另加一条「老板岗位绑定视为租户级」的特例。
  - 两者影响：一人多企不存在（D14），但「老板换人」「第二个老板」的行为不同。**拍板前不得实现**。
- **员工状态是否含「待激活」⬜**：入企三合一（邀请码 / 手机号白名单 / 老板预建）意味着员工记录可能**先于登录存在**。是先建成 `在职` 再等登录，还是 `待激活 → 在职`，未定。
- 员工**不含**所属公司字段：所属公司由 §1.5 推导（一人可绑多个公司，D15）。员工档案（履历等）二期（D6b），一期只有账号 + 岗位分配。

### 1.6 员工-权限覆盖 `employee_permission_override`

| 字段 | 语义类型 | 必填 | 约束 / 说明 | 来源 |
|---|---|---|---|---|
| 员工 id | 引用 → 员工 | ✅ | | D50 |
| 功能域 | 枚举 | ✅ | 同 §1.4b | D50 / D44 |
| 动作 | 枚举（8 动作） | ✅ | | D50 / D4 |
| 是否授予 | 布尔 | ✅ | `true` = 在岗位并集之上**加**；`false` = **减**（个人覆盖优先于岗位基线） | D50 |
| 操作人 | 引用 → 员工 | ✅ | 谁改的（经理/老板），另进审计 | D50 / D51 |
| 更新时间 | 时间点 | ✅ | | — |

**约束与坑**
- 唯一键 `(员工, 功能域, 动作)`；一个 `(员工,域,动作)` 只能有一条覆盖行，**不能既加又减**。
- **覆盖的维度 ⬜（未定 + TODO，最容易写错）**：D50 说「对单个员工单独开关某项权限」，没说是否**按公司细分**。当前 `openapi.yaml` 的 `PermissionOverride` 只有 `domain/action/granted`（无 companyId）→ 一期按「员工级、跨公司统一生效」。若将来要按公司细分，唯一键与并集算法都要变。**在拍板前，不得在解析层预留「看起来支持但其实没实现」的 companyId 字段**（会造成事实冻结）。
- **覆盖不能突破公司集合**：`granted=true` 只能改变「能不能做这个动作」，**不能**让员工看见未绑定公司的数据（D15）。即 `覆盖 ⊆ 公司集合` 是硬不变量（见 §2.3 不变量 I4）。
- **谁能改谁（写侧边界，D50）**：经理可改普通员工（销售/售后、采购、质检、理货、拣货…），**不可改老板、财务、其他经理**；老板全权。这是**判定引擎之外的第二个判定**（目标人保护），见 §2.4 步骤 9。
- ⬜ **经理能否改自己的权限**未定（D50 只列了目标人类型，未含「自己」）。**默认按拒绝实现前必须先拍板**。
- 覆盖行的**有效期**：一期不做（D50 未提）；临时增减靠人工改回。⬜ 若需要「到期自动失效」另立。

- **待办是通知，不是状态判断**（D8）：待办的完成**不得**反向推进单据状态；单据状态仍由人工修改（规则 #6）。
- **去重**：同一单据同一次状态变更只能产生一条待办。唯一键候选 `(单据类型, 单据 id, 变更后状态, 事件序号)`；「事件序号」怎么来 ⬜（可用单据版本号，取决于单据框架是否强制版本，📄 ADR 提议乐观锁）。
- 待办的可见性：工作台对全员开放，但**待办列表按权限过滤**（D44）——过滤逻辑走 §2，不在待办表里冗余权限字段。

- ⬜ 流转表的作用域（租户级 / 公司级）、是否有出厂种子行、一期是否提供配置界面，三项均未定（D8 只说「留作配置扩展」）。

### 1.9 操作日志 `audit_log`

字段清单与**失败语义**见 §4（契约第三批 §1 + D51）。本节只记结构性约束：

- 金额/成本字段进 `变更摘要` 前按「看价」脱敏（D27 / D51）；**写入前脱敏 vs 查询时脱敏** 📄 ADR 提议写入前（避免日志本身成为越权数据源），未拍板 ⬜。
- 索引/查询维度（逻辑）：`(租户, 时间倒序)`、`(租户, 动作)`、`(租户, 操作者)`、`(请求 id)`。物理索引见 §5。

## 2. 权限引擎判定契约

> 目标：**8 个业务模块只调用一个判定入口，不各自重写权限**（AGENTS.md「权限服务端判定」；D15/D27/D50/D52.1）。
> 引擎是**纯判定**：不写库、不发通知、不做业务校验、不缓存授权结果。业务规则（改价下限 D20、库存可用量 D38、取消级联 D21 等）属于各用例，**不要塞进引擎**。

### 2.1 输入

| 输入项 | 语义 | 必填 | 来源 |
|---|---|---|---|
| 主体（principal） | 由凭证解析得到：`操作者类型`（platform / employee / ai / system）、`员工 id`、`租户 id`、`凭证类型`（session / token）、`凭证 id`（AI = token id）、`请求来源`（web / cli / api / mcp / job） | ✅ | §1 / §3 |
| 公司（目标数据范围） | 本次操作**要触碰的公司 id**；查询类可为「待过滤的公司集合」 | 写操作 ✅ / 查询 ✅ | D15 / D22 |
| 功能域 | D44 的 19 项之一（或 `platform` 平台域） | ✅ | D44 |
| 动作 | 8 动作之一：查 / 建 / 编 / 审 / 出库 / 删 / 看价 / 导出 | ✅ | D4 |
| 请求体（body） | 只读摘要，供**条件判定**（如目标人的身份、是否危险动作、是否涉及金额字段）与审计摘要；**引擎不据此做业务规则校验** | 写操作 ✅ | §3 |
| 预检标记 | `dryRun`：判定与真实执行**走同一条路径**，只是不落库 | 选填 | §3 |

### 2.2 输出

```
判定结果 = {
  decision: allow | deny
  reasonCode: <封闭枚举，见 2.5>
  effective: {                       // 仅 allow 时有完整值；deny 时可为空（避免泄漏）
    companyIds: [公司 id ...]        // 数据可见范围（老板 = 全租户公司）
    permissions: { 功能域: [动作 ...] }  // 已含 ⊕ 覆盖、∩ 公司集合、∩ token scope
    priceVisible: true | false       // 「看价」结论（决定金额字段是否脱敏，不决定 allow/deny）
  }
  auditHints: {                      // 供审计写入，避免上层重复推导
    actorType, actorId, credentialId, source, reason 是否必填
  }
}
```

- **allow 不等于「能写」**：引擎只回答「这个主体能不能对这个功能域做这个动作、能不能碰这个公司」；`If-Match` 版本冲突、幂等键冲突、业务校验失败都发生在引擎**之后**（§3 的错误码）。
- **deny 必须带可解释原因码，但不得泄漏他人数据**：跨公司越界一律按「不存在」处理（openapi `NotFound` 明确「不泄露存在性」），不要回「该单据属于公司 X」。

### 2.3 判定顺序（顺序即契约，任何实现不得重排）

```
0. 租户闸门：企业存在且状态=启用        → 否则 TENANT_NOT_ACTIVE
1. 员工闸门：员工存在且状态=在职        → 否则 EMPLOYEE_DISABLED（AI 同步立即失效，D52.1②）
2. 凭证闸门：token 状态=active、未过期、IP 命中白名单
                                        → 否则 CREDENTIAL_INVALID
3. 岗位并集基线：
   base(域,动作) = ⋃{ 岗位授权 | 岗位 ∈ 该员工在「绑定公司集合」内的全部绑定 }
4. 个人覆盖（D50）：
   final = base ⊕ override        // override=true 加、false 减，个人覆盖优先
5. 公司集合（D15）：
   companyIds = 员工绑定的公司集合；老板 ⇒ 全租户公司
   ├─ 目标公司 ∉ companyIds        → COMPANY_OUT_OF_SCOPE（对外表现为 NOT_FOUND）
   └─ 结论按公司分别成立：允许在 A 公司做的动作，不自动允许在 B 公司做
6. token scope（D52.1①）：
   若 凭证类型 = token：final = final ∩ scope
   ├─ 域/动作不在 scope 内         → SCOPE_NOT_GRANTED
7. 动作闸门：(域,动作) ∈ final     → 否则 ACTION_NOT_GRANTED
8. AI 危险动作闸门（D52① 🟡）：
   危险动作集合 = {删除, 冲正, 成本更正, 结算确认, 权限变更}
   ├─ 操作者 = ai 且 未开「允许 AI 走审批」 → AI_ACTION_FORBIDDEN
   └─ 已开 → 仍要求走审批 + reason 必填（引擎放行，审批由审批框架处理）
9. 审批人闸门（D52.1③）：
   ├─ 操作者 = ai 且 动作 ∈ {审批通过, 审批驳回}      → APPROVER_MUST_BE_HUMAN
   └─ 操作者 = ai 且 该动作的发起人就是本 AI 的委托人 → APPROVER_MUST_BE_HUMAN（不得审批自己发起的）
10. 目标人保护（D50）：
    若操作对象是员工本人或他人权限（改覆盖 / 改岗位绑定）
    ├─ 操作者 = 经理 且 目标 ∈ {老板, 财务, 其他经理}  → TARGET_PROTECTED
    └─ 目标 = 操作者本人                            → SELF_OVERRIDE_FORBIDDEN（⬜ 见 6-M1，未拍板前不启用）
11. 看价标记（D4/D27）：
    priceVisible = (view_price ∈ final)           // 不产生 deny，只产出脱敏标记
→ allow（携带 effective）
```

**为什么这个顺序**（容易写反的地方）：
- **公司集合必须在动作闸门之前**（步骤 5 先于 7）：先按公司裁掉可见范围，再谈动作，否则「员工在 A 公司有权、在 B 公司无权」会被并集成全局有权。
- **token scope 必须在个人覆盖之后**（步骤 6 后于 4）：AI 的 scope 只能**收窄**人给它的权限，不能反过来把员工没有的权限补出来。顺序反了就会出现「AI 比人权限大」——直接违反 D52.1。
- **看价永不 deny**：它只决定响应里的金额字段是否脱敏。任何把 `view_price` 写成「没有权限就 403」的实现都会把「能看单但不能看价」的员工彻底挡在单外（D4/D27 明确要「可见记录、金额隐藏」）。

### 2.4 不变量（可用测试钉死）

| # | 不变量 | 依据 |
|---|---|---|
| I1 | `effective ⊆ 岗位并集 ∪ 个人覆盖`，且 `effective ⊆ scope`（AI） | D4 / D50 / D52.1 |
| I2 | 每请求重算，**授权结果不跨请求缓存**；员工停用/改岗/改覆盖后下一次请求立即生效 | D52.1② |
| I3 | 相同输入 + 相同数据快照 ⇒ 相同输出（判定是纯函数） | — |
| I4 | 个人覆盖**只能改动作**，不能扩大公司集合 | D15 / D50 |
| I5 | 老板命中租户级短路时，**仍受 token scope 与 AI 危险动作闸门约束**（老板 + AI 也不是超级权限） | D52.1⑤ |
| I6 | `dryRun` 与真实执行走同一条判定路径，**不允许 dryRun 跳过任何闸门** | §3 |
| I7 | AI 的生效权限**恒 ⊆ 绑定员工当次生效权限**（禁止任何「平台侧/系统级」旁路） | D52.1⑤ |

### 2.5 原因码（封闭枚举，**提案**）

> 原因码是**引擎内部**的判定结论；HTTP 层再映射到契约第三批 §3 的统一错误体。`openapi` 的 `ErrorCode` 枚举本身也是**提案**（契约只约定错误体结构，未枚举 code），因此两张表都需在契约冻结时一并确认。

| 原因码 | 含义 | HTTP | 错误体 code（提案） |
|---|---|---|---|
| `OK` | 放行 | 2xx | — |
| `TENANT_NOT_ACTIVE` | 企业不存在或已停用 | 403 | `FORBIDDEN` |
| `EMPLOYEE_DISABLED` | 员工停用/离职（AI 同） | 401 | `UNAUTHENTICATED` |
| `CREDENTIAL_INVALID` | token 撤销/过期/IP 不符/会话失效 | 401 | `UNAUTHENTICATED` |
| `COMPANY_OUT_OF_SCOPE` | 目标公司不在可见集合 | 404 | `NOT_FOUND`（不泄露存在性） |
| `ACTION_NOT_GRANTED` | 功能域 × 动作未授权 | 403 | `FORBIDDEN` |
| `SCOPE_NOT_GRANTED` | token scope 比人窄 | 403 | `FORBIDDEN` |
| `AI_ACTION_FORBIDDEN` | AI 危险动作默认拒绝 | 403 | `AI_ACTION_FORBIDDEN` |
| `APPROVER_MUST_BE_HUMAN` | 审批只能人类（含自审拦截） | 403 | `FORBIDDEN`（⬜ 是否单列 code 未定） |
| `TARGET_PROTECTED` | 经理改老板/财务/其他经理 | 403 | `FORBIDDEN` |
| `SELF_OVERRIDE_FORBIDDEN` | 改自己的权限（⬜ 未拍板，暂不启用） | 403 | `FORBIDDEN` |
| `REASON_REQUIRED` | 危险动作/AI 写操作缺 reason | 422 | `VALIDATION_FAILED` |

### 2.6 「看价」数据可见性子契约（D4 / D27 / D51）

**输入**：`priceVisible`（§2.3 步骤 11）。
**输出**：字段级脱敏指令，由**序列化层统一执行**，不在各模块里各写一遍。

| 范围 | 受管字段 | 无 `view_price` 时 |
|---|---|---|
| 单据 | 单价、金额、总售价、总成本、毛利、毛利率、提成比例、提成金额 | 隐藏金额（形态 ⬜） |
| 成本 | 批次锁定单价、成本构成各项、费用行金额 | 同上 |
| 损失 | 全损耗损失金额（D27 明确「可见损失记录、金额隐藏」） | 记录可见、金额隐藏 |
| 收款 | 收款/退款金额、块内余额 | 同上 |
| 审计 | `变更摘要` 里的金额与成本字段 | 同上（D51 要求口径一致） |

**硬约束**
- 脱敏**必须服务端做**（D15/D27）；前端隐藏不算数。
- **记录可见性 ≠ 金额可见性**：无 `view_price` 时列表/详情仍返回该行，只是金额字段被掩掉（D27「可见损失记录但金额隐藏」）。
- 无权限时返回 `null` 还是省略键，⬜ 未定（本文建议 `null` + 显式 `masked: true` 标记，需契约冻结确认；**不得各方自行选择**）。
- 导出（`export` 动作）必须继承同一脱敏结论：`export` 与 `view_price` 是两个独立动作（D4），**有导出权不等于能导金额**。

## 3. 编号取号与并发安全

### 3.1 规则（已拍板，D16 / D48）

| 编号 | 结构 | 长度 | 唯一性 | 重置 |
|---|---|---|---|---|
| 单据号 | `类型字母`-`公司码`-`日期`-`流水` | 1+1+4+1+8+1+4 = **21 位** | 租户内全类型合起来唯一（由完整字符串保证） | **流水按月重置** |
| 工号 | `六位数字` | **6 位** | **全租户全局唯一**、不带公司前缀、跨公司调动不变 | 不重置 |

- 类型字母（8 类，D9/F7）：A 采购 / B 加工 / E 销售 / N 内部 / C 结算 / R 客户退货 / S 供应商退货 / I 盘点。
- 公司码 4 位 `0001`~`9999`，租户内全局顺序递增，**固定带、不设开关**（D16）。
- 流水 4 位 `0001`~`9999`，**按月重置**。
- 日期 8 位 `YYYYMMDD`。

### 3.2 必须先拍板的三个前置（否则并发方案无从谈起）

| # | 未定项 | 为什么卡住实现 | 候选 |
|---|---|---|---|
| N1 | **流水的计数键粒度**：`(租户, 公司, 类型, 年月)` 还是 `(租户, 公司, 年月)` 共享流水 | 决定容量与去重键。D16 只说「单公司月内 9999 单」，没说是否按类型分开 | ①按类型分开（容量 = 类型数 × 9999，更宽松）；②全类型共享（容量 9999/月，但「单公司月内 9999 单」字面如此） |
| N2 | **日期取哪个时区**：服务器 UTC / 租户时区 / 公司时区 | 跨月 0 点并发必须知道「哪一天算 1 号」；UTC 与东八区差 8 小时，**会直接造成月初号码错位或重复** | ①租户时区（与「按租户时区展示」一致）；②公司时区；③UTC |
| N3 | **是否允许号段空洞**：业务事务回滚后号码是否回收 | 「同事务取号」必然跳号；「独立事务取号」则不跳号但要额外锁与容错 | ①允许跳号（推荐，简单且不可回收）；②不允许跳号（需独立取号事务，回滚语义复杂） |

> 这三点本文只列候选，**不写默认值**。N1/N2 属口径（可由 Lead 拍板后追加 decisions），N3 属口径 + 实现取舍。

### 3.3 并发安全方案（思路与约束，不写代码）

**总原则：先靠数据库的唯一约束兜底，再靠原子自增消除竞争，最后靠幂等键挡住重试。**

1. **唯一约束是最后防线（不可省）**
   对「单据号」建唯一约束（作用域 = 租户内；工号类同）。任何取号结果重复，写入必然失败——**绝不允许「取到号就写成功」而依赖调用方自觉去重**。
   意义：就算并发控制写错，也只会**报错**，不会**两单同号**。

2. **计数表 + 单行原子自增（首选机制，与语言无关）**
   - 一张计数表，逻辑键 = N1 拍板后的粒度；值 = 已发放的最大流水。
   - 取号 = **一条原子「取新值并返回」的操作**（`UPDATE ... SET 值 = 值 + 1 WHERE 键 = … RETURNING 值` 语义；首次使用用 `upsert` 建行）。
   - 为什么靠原子自增而不是「先读再写」：读-改-写在并发下必然撞车，靠重试兜底会把错误推到临界点（跨月 0 点最明显）。
   - **不需要**外部锁、Redis、MQ（ADR 规模结论：月单量 < 50，性能不是理由）。
   - 备选：`SELECT ... FOR UPDATE` 行锁串行化。更保守、更易评审，但会持有行锁到事务结束；在「取号与业务同事务」的模型下会成为热点，规模小可接受。**二选一须在 D53 后定到底层能力再选**（见 §5）。

3. **跨月重置 = 换键，不是清表**
   - 重置靠**计数键里带「年月」**天然实现：新月份 = 新键 = 从 `0001` 开始。
   - **不要**写「定时任务在 0 点把计数清 0」：定时任务失败/漂移会造成重号；换键是幂等且无状态的。
   - 跨月 0 点的用例必须覆盖：「同一秒内，一单落在 23:59:59、一单落在 00:00:00，两单在 N2 口径下属于不同月份」→ 结果是两个不同的键各自 `0001`，**不冲突**；若 N2 取 UTC 而业务以为本地，则会出现「1 号凌晨的单仍是上月流水」这种**看起来像重号、实际是口径错**的 bug。

4. **工号取号**
   - 同一套机制，计数键 = `(租户, 'employee')`，**租户级、不带公司**（D48 明确不带公司前缀）。
   - 与单据号的区别：**不做按月重置**，全局单调递增。
   - 员工停用/删除（若允许）**不回收工号**：D48 说编号是稳定主键，回收会破坏溯源。

5. **容量耗尽必须显式失败**
   - 流水 > 9999 / 公司码 > 9999 / 工号 > 999999 时：**拒绝取号并给出明确错误**，禁止回绕、禁止溢出成 5/7 位（会破坏定长结构与解析）。
   - ⬜ 容量耗尽的处置策略（拒绝建单？提前预警？扩位方案需改 D16）未定——扩容等于改 D16，属「先改 decisions 再改代码」。

6. **取号与业务事务的关系（依赖 N3）**
   - 若允许跳号：取号在业务事务内完成，失败回滚即弃号。**最简单，也是本文推荐**。
   - 若不允许跳号：取号必须在独立事务提交后再执行业务，业务失败要走「退还号码」逻辑——退还本身又要防重号，**实现复杂度陡增**，且与「只追加」的审计精神相悖。
   - ⚠️ **幂等键不等于取号幂等**：写接口带 `Idempotency-Key`（24h）时，重试必须**命中首次结果、不再取号**；否则一次客户端重试会白烧两个号（若选「不跳号」还会直接错位）。

7. **dryRun 不得消耗号码**
   预览类请求（`dryRun=true`）全程不落库、**不推进计数器**；因此 dryRun 返回的「将要使用的号码」只是**预测值，可能与他人并发冲突**——返回时必须标注它是预测值（⬜ 是否在响应里给「预测单号」未定，建议不给，避免用户拿预测号去线下用）。

8. **并发安全必须有的测试用例（写实现前先写）**
   - 同一 `(公司, 类型, 年月)` 并发 N 单 → 号连续且无重复（N > 并发数阈值）。
   - **跨月 0 点**：23:59:59 与 00:00:01 各一单，符合 N2 口径。
   - 业务事务失败回滚 → 该号不被复用、后续号正常（依 N3）。
   - 唯一约束触发 → 返回明确错误而不是 500 裸抛。
   - 满号边界：9999 之后必须报错。
   - 并发建员工 → 工号连续、无重复、不带公司前缀。
   - 带 `Idempotency-Key` 重试 → 只消耗一个号。

## 4. 审计写入的失败语义与字段清单

### 4.1 失败语义（D51 + ADR U5 📄）

**U5 的拟定默认是「阻断业务」**（📄 ADR，未拍板）：审计写不进去就**不返回业务成功**，返回 500 + 告警，**不接受「审计失败但业务成功」**（因为 D51 要求全量）。

这个默认值必须被精确限定到「**哪个时刻的失败**」，否则实现会走偏。三个失败点：

| # | 失败点 | 业务是否已提交 | 处置 | 依据 |
|---|---|---|---|---|
| F1 | **提交前**：业务事务内写审计缓冲（outbox 语义）失败 | 否 | **整个业务事务回滚，返回 500 + 告警**。这是 U5 真正覆盖的场景 | D51 / U5 📄 |
| F2 | **提交后**：业务已提交，审计从缓冲搬到只追加日志时失败 | **是（不可回滚）** | **无法阻断**。只能：①至少一次重投（追加器幂等，按缓冲行去重）；②失败即告警；③每日对账（业务写入数 vs 审计数）差异告警 | D51 + R2 📄 |
| F3 | **无业务事务**：业务本身失败（403/422/409），只写一条 `result=fail` 的日志，这条也写失败 | 否（业务已失败） | 仍返回错误 + 告警。⬜ **返回哪个错误未定**：原业务错误码（422）还是审计基础设施错误（500）？建议 500（漏记是硬违规，不能被 422 掩盖），需拍板 | D51 |

**必须在文档层面说清的两句话**（非常容易被实现成错的）：
1. **U5 的「阻断」只覆盖 F1**。F2 在物理上无法阻断——任何声称「提交后失败也能阻断」的实现都是在骗自己，最后结果就是**静默漏记**（违反 D51 更严重）。
2. **审计写入失败不得被吞**：不允许 `try { 写审计 } catch { /* 忽略 */ }`。宁可 500，不可漏记（D51 全量是硬要求）。

**只追加的强制手段**
- 应用层：不暴露任何更新/删除日志的接口与仓储方法（D51）。
- 数据层：对日志表**只授 INSERT**（回收 UPDATE/DELETE 权限）或用触发器拦截。📄 ADR 提议，**具体手段依赖数据库能力 → 进 §5**。
- 平台侧保留独立副本：租户删除任何数据不影响日志（契约 §1）。

**记录规则**
- 写操作全量 + 敏感读（导出 / 看金额 / 看日志）记录；**普通列表与详情查询不记**（D51① 🟡 默认，待确认）。
- 覆盖清单（契约 §1）：登录 / 登出 / **失败登录**、权限与岗位变更、个人权限覆盖、API Token 增删改、全部写操作、导出、查看敏感金额、查看操作日志、**AI 全量调用**、平台运营后台全部操作。
- **查看日志本身也记日志**，但不递归（为「查看日志」那条读日志，不再生成新的读日志）。
- AI 调用额外记：token id（凭证 id）、来源、reason（契约 §1 / D51）。
- 保留期：云端 ≥ 180 天，到期归档不物理删除（D51② 🟡 默认，待确认）。
