## 1. 一句话

**轻单 = 面向建材 / 家居 / 日用行业的「订单成本核算 + 进销存」系统，对外销售的 SaaS；核心是把一张订单的全部成本来源挂到订单上，实时算出真实成本与毛利（一单一成本、一单一毛利、可追溯到批次与经手人）。**

- 定位口径已由 `轻单_项目上下文说明_v1_20261103.md` §1 收紧（**不是 ERP、不是财务软件、不是通用进销存**）；本文件早期版把它写成「订单 + 库存 + 人员权限系统」是过度简化，已作废。
- 产品性质已于 2026-11-03 拍板：**对外 SaaS**（不是集团内部专用），详见 `docs/decisions.md` D1。
- **行业定位**（D17）：一期**数据模型行业中立**（不写死行业字段、界面文案不带行业词），业务锚定**家具/建材**做深跑通（一单 1-2 种商品、几千到几万、单公司月单量 < 50）；多行业模板推二期。
- 「可视化」原文写「期望各成员尽快完善掌单的功能可视化界面」；该诉求已拍板定位为**手段**（一期做业务全流程图，实时看板二期），见 `docs/decisions.md` D7。

**权限模型已于 2026-11-03 升级**（见 `docs/decisions.md` D4）：原「8 岗位 × 11 功能行」二维矩阵**降级为出厂默认值**，实际模型是「**预设岗位 + 自定义岗位**」——老板可在预设岗位上增减权限，或新建自定义岗位；授权粒度是**功能域 × 动作**（8 动作：查/增/改/删/审批/授权/导出/看价格）；员工可**一人多岗，权限取并集**；「仓管员」不是新列，而是预设权限包（理货 + 拣货 + 质检查看）。矩阵还要加**公司维度**（一个租户内多子公司）。

## 3. 业务领域（原始权限表行名共 11 项；**功能域已拍板扩展，清单待定稿**）

原文 11 项：权限设置、商品资料、库存数量、商品成本、订单/状态、采购单、退货单、报价单、客户、供应商（商品资料分支）、货物位置

原文四块划分（**推断**，仅用于理解原表）：

| 块 | 包含 |
|---|---|
| 单据流转 | 订单/状态、采购单、退货单、报价单 |
| 主数据 | 商品资料、客户、供应商、货物位置、商品成本 |
| 库存 | 库存数量、货物位置 |
| 组织 | 权限设置、员工 |

**2026-11-03 拍板后的真实功能域**（`docs/decisions.md` D2/D3/D9 选全量 + 冲正）：以 **A 采购 / B 加工 / E 销售 / N 内部交易 / C 结算 / 冲正单据（R 客户退货 · S 供应商退货 · I 盘点）** 六类为骨架，仓库那 6 种单据降级为业务动作或库存流水类型；相对原 11 项，**新增**：加工单、结算/毛利、库存流水、加工厂档案、提成、内部交易、公司管理、冲正单据、利润报表；**删除**：报价单（一期不做报价测算）、货物位置（二期）；集团看板一期不做（D45）。**完整功能域清单已由 D44 定稿**（`docs/decisions.md` §1）。

## 6. 交付形态与顺序（已知，2026-11-03 用户确认；性质已拍板）

**一期 = 云端 SaaS 订阅版单一形态**（2026-11-03 拍板，见 `docs/decisions.md` D1）：软件与运行数据在我们云端，云端是唯一记账真相；客户本地只保留**只读备份副本**（自动推送 / 定期核对，断网只可看不可改，修改一律联网）。**买断版（部署到客户自己的云服务器）推二期**，一期内买断诉求用「永久授权 + 数据可完整导出」兜底。

客户端形态仍按四端推进：

**先做网页端，再依次扩到 Windows 桌面端 → Mac 端 → 安卓应用端；鸿蒙暂不考虑。**

| 顺序 | 平台 | 状态 |
|---|---|---|
| 1 | Web（浏览器） | 先做 |
| 2 | Windows 桌面 | 后续 |
| 3 | macOS 桌面 | 后续 |
| 4 | Android 应用 | 后续 |
| — | 鸿蒙 | 明确不做 |

**推断（待确认）**：四端顺序意味着不该写四遍。可选的收敛方式是一套 Web 代码 + 各端外壳（Windows/macOS 用 Electron 或 Tauri，Android 用 Capacitor 之类），权限与业务逻辑在后端一处生效。**这是建议，不是已定方案。**

由此带来的硬约束（无论选哪种实现都成立）：

- 业务规则（尤其模块 × 角色权限矩阵）必须**服务端集中判定**，不能散在四端各自实现——否则四端一致性无法维护。
- 桌面端与安卓端都要求**离线/弱网**时的行为有明确定义，这一项目前完全没有材料。

## 7. 开发路线（已知，2026-11-03 用户确认）

1. **产品原型**：用户与 DSH 一起把原型做到「完善」——信息架构、页面、字段、操作、权限、数据关系都要能落地。
2. **分工**：原型定稿后**分模块交给其他团队成员开发**（多智能体并行，每人一个模块）。
3. **合并**：各模块合回主干。
4. **迭代**：合并后再扩展或修改功能。

由此产生的硬性要求：

- 原型必须细到**字段级**，否则分模块开发的几个人会各自发明一套字段名和状态值，合并时对不上。
- 模块切分、**接口契约与数据模型**要在分工前冻结；并行开发的代价是任何契约变更都要各模块同步改。
- **画板内容不补了**（用户 2026-11-03 明确）：9 张画板（订单结构图、用户基础工作流程图、项目分工图、客户/仓库/订单/账号、2×思维导图）不再作为输入。**但 2026-11-03 拍板 D3=(a) 后，原型的依据不再是「权限表 11 个业务域」**，而是 v1 交接文档的五类单据骨架（A/B/E/N/C）+ 成本归集；权限表只提供「岗位默认权限」，不提供价值链。
- **契约分两批冻结**（D3）：第一批 A/B/E/C 主链 + 批次 + 库存流水；第二批 N 单 + 提成 + 内部定价。两批互不阻塞。
- **真源口径**（D0）：v1 交接文档是口径真源（L1/L2），仓库 `docs/` 是产出层（L3）；**已拍板结论集中在 `docs/decisions.md`**，冲突以它为准。

## 9. 约束与非目标

- **术语**：正名 **轻单**。飞书原文里的「掌单」是原作者用词，原料区不改写；产出文档一律写「轻单」。
- **原料不改写**：`docs/raw/` 只存原文，改写产出放 `docs/` 根下。
- **不猜规格**：本文件任何「推断」都不得直接当验收标准；模块规格以阶段 3 与用户逐条确认为准。
- **非目标**：不做通用 ERP、不做财务记账与开票、不做生产排产（`decisions.md` D2/§4）。~~不做多租户 SaaS~~ **该句已作废**：2026-11-03 拍板产品性质为对外 SaaS（D1），原「除非第 2 题答案推翻」的条件已触发。
