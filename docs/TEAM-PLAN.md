# 轻单 · 四人协作开发计划（人类开发者版）

> **读者**：4 位协作开发者 + 项目负责人。
> **配套**：`docs/ONBOARDING.md`（接入流程）、`docs/DEV-SETUP.md`（环境与目录）、各模块 `docs/module-<模块>.md`（你的边界与验收）。
> **状态**：2026-11-04 起草；技术栈待 D53 拍板、接口契约第三批待冻结、代码骨架未建（见 §8 当前阻塞）。

## 1. 分工（一个人 = 一组模块，写范围互斥）

| 代号 | 负责模块（分支） | 工作量 | 为什么这样分 |
|---|---|---|---|
| **Dev A** | `platform`（`feat/platform`）+ `test` 底座 | ★★★ 最重，必须最先 | 登录/权限/编号/审计/审批/单据框架/待办/API 层是全项目地基；只有一个人能改，避免公共层被并行改花 |
| **Dev B** | `masterdata`（`feat/masterdata`）、`purchase`（`feat/purchase`）、`internal-trade`（`feat/internal-trade`） | ★★ 主数据轻、后两个依赖库存 | 采购与内部调货同属「进货/调货」心智，主数据先做给全组解锁 |
| **Dev C** | `inventory`（`feat/inventory`）、`processing`（`feat/processing`） | ★★★ 库存是账实真相 | 批次/可用量/流转/成本更正与加工损耗强耦合，放一个人做最不容易对不上 |
| **Dev D** | `sales`（`feat/sales`）、`settlement`（`feat/settlement`） | ★★★ 销售 + 结算/提成/报表 | 收款、退款、C 单重算、提成快照是一条链，拆开会天天跨人改 |

> 名字待填：把 4 位同事的姓名/常用 ID 填进上表（`Dev A` → 真名），并同步 `docs/ONBOARDING.md` §4 的「负责人」列。
> **一人多模块时**：同一时间只推一个模块，另一个模块的分支可以空着，避免自己两个分支互相 rebase 打架。

## 2. 依赖顺序（谁能先动、谁必须等）

```
platform ──► masterdata ──► inventory ──► purchase ──┐
     │                        │              processing ─┼──► settlement
     │                        └──────────────► sales ───┘
     └──────────────────────────────────────► internal-trade ──► settlement
```

- **platform 是唯一硬前置**：A 没交付「权限判定 + 编号 + 审计 + 单据框架 + contracts 包」之前，B/C/D 不要写业务代码。
- 但 B/C/D **不是干等**：第 1 周做「契约落地 + 数据模型 + 用例清单 + 测试清单」，具体见 §4。
- settlement 等 sales/processing/internal-trade 的接口稳定后再开，避免 C 单算错。

## 3. 里程碑（以周为单位，按 7 周排）

| 里程碑 | 目标 | 交付物 | 谁 | 验收方式 |
|---|---|---|---|---|
| **M0（第 0 周）** | 开工前置全部清掉 | D53 拍板、契约第三批冻结、仓库骨架（5 个包 + ESLint + 迁移 runner） | Lead + Dev A | `pnpm install && pnpm -r build` 通过；`tests/run.ps1` 绿 |
| **M1（第 1 周）** | platform 可用 | 登录/入企、权限三层、编号、审计写入口、审批骨架、单据框架、待办、OpenAPI 可产出 | Dev A | platform 验收清单；OpenAPI 文档可访问 |
| **M2（第 2 周）** | 主数据 + 库存基础 | masterdata CRUD + 默认售价；批次入库/四列/流水/盘点调整 | B、C | 各自模块验收；L2 用例测试绿 |
| **M3（第 3 周）** | 单据主链 | A 采购 + S 退货；B 加工（含全损耗/损失记录） | B、C | 单据全链路：A → 批次 → B → 新批次 |
| **M4（第 4 周）** | 销售与收款 | E 单（改价下限/费用行规则）+ 收款记录 + 在线支付（模式 A）+ R 客户退货 | D | E 单 → R 单 → 收款负数行 |
| **M5（第 5 周）** | 内部交易 + 结算 | N 单（在途锁定/转司）；C 单（自动草稿/确认/毛利/损失/净毛利/提成快照） | B、D | 跨公司调货闭环；C 单数字与手工核算一致 |
| **M6（第 6 周）** | 报表 + 打印 + 集成 | 利润报表（未归属损失下钻）、两套打印版式、导出、CLI/MCP 端到端 | 全员 | CLI 完成一单全流程；MCP 工具可列可调 |
| **M7（第 7 周）** | 联调与验收 | 端到端用例、性能基线、部署脚本、只读备份、验收报告 | 全员 | 验收清单逐条签字 |

> 周数按「4 人全职」估；如果大家是兼职，按比例顺延，但**里程碑顺序不变**。

## 5. 协作节奏

| 节奏 | 内容 | 产出 |
|---|---|---|
| 每日 15 分钟（文字即可） | 昨天做完 / 今天做 / 有没有被卡 | 发在群或 Issue；被卡的当天升级 |
| 每周一次 30 分钟复盘 | 里程碑进度、契约变更、遗留问题 | `docs/roadmap.md` + 各自模块检查点更新 |
| 每个 PR | 按 `.github/pull_request_template.md` | CI 绿 + 1 人 approve |
| 每次口径变更 | 先改 `docs/decisions.md`（只追加）→ 改契约 → 再改代码 | 变更记录 |

**PR 规则**：单个 PR 建议 ≤ 400 行 diff；超过就拆。评审 24h 内响应。谁提的谁合并（评审后）。

**阻塞升级**：同一问题卡 4 小时 → 找 Dev A（技术）/ Lead（口径）；口径问题一律由 Lead 拍板并落 `decisions.md`，不许在代码里"先按我的理解写"。
