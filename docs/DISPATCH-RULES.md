## 七、红线 PR、冲突、口径分歧怎么处置

**红线 PR 的汇报格式（判读卡，四段缺一不可）**——负责人靠这四段决定合不合，写不出四段就等于没汇报：

1. **改了什么**：逐条列红线文件的改动与增删行数；迁移文件名与编号；`docs/decisions.md` 新增条目原文；`packages/contracts/src/domains.ts` 的域/动作变更。
2. **冲突在哪**：`conflictFiles` 的具体文件；再说清两边各改了什么（`git diff origin/main...origin/<branch> -- <file>`），冲突是「同处改写」还是「各自新增同号迁移」。
3. **与口径是否一致**：逐条对照 `docs/decisions.md`、`AGENTS.md`（权限模型铁律等）、`docs/OWNERSHIP.md`，明确列出「一致项 / 不一致项」。
4. **结论三选一**：可合（写明凭据）/ 对方方案更好 → 先请求负责人同意再改 / 不如口径 → 退回改。

**口径分歧的处置顺序（2026-11-16 负责人口径）**：

- **对方方案优于现口径** → 不许自己改口径，先在 issue/PR 里提「他的做法是 X，比现口径 Y 好在 Z，建议采纳」，**拿到负责人明确同意后**再改 `docs/decisions.md` 与代码。
- **对方方案不如现口径、或验收不达标** → 退回作者改，写清具体改法 + 验收命令；不代写（红线除外，红线本来只有主线能改）。
- **拿不准谁更好** → 把两边摆出来让负责人选，不替他选。

**迁移编号撞车**：多个 PR 抢同一编号时先定合入顺序，后合的把号顺延并在 PR 里注明；同一编号绝不允许存在两个文件。

### 判「谁更好用」的三条标尺（2026-11-16 负责人口径）

原话：「秉承一个精神，开发多花钱，维护更新少花钱。」并补充：「要产品更高的质量与性能。」

判优劣**同时**看这三条，缺一条的判定不成立：

1. **维护与更新成本** —— 少加结构、少加开关、少让人记住额外的约定。但**不许靠借用相邻权限或借用别的域来省**（这是把成本推给以后，不是省）。
2. **产品质量** —— 可回滚、审计留痕、错误态与边界写清、口径单一真源；能补的缺陷当场补（如迁移的 backfill），不留成「下一个人踩」。
3. **性能** —— 查询与渲染代价：有没有 N+1、有没有全表扫、索引跟不跟得上、分页与聚合放在哪一层。

三者冲突时：**先保质量与性能，再谈省维护成本**；三条都不能当作绕开红线或权限铁律的理由（「省事」不是理由，「更快」也不是）。

## 八、巡检出勤节奏与节假日（2026-11-16 负责人定）

| 日子类型 | 出勤时刻 |
|---|---|
| 工作日、调休上班日 | 06:00 / 12:00 / 18:00 / 24:00（即次日 00:00） |
| 周末、法定节假日 | 06:00 / 09:00 / 12:00 / 15:00 / 18:00 / 21:00 / 24:00 |

- 实现方式：调度器**每天**在 06/09/12/15/18/21/00 七个整点唤醒，由 `hourly-patrol.ps1 -Mode daytype` 判当天日子类型与应出勤时刻；`shouldRun=false` 的整点直接跳过（工作日不出勤 09:00 / 15:00 / 21:00）。RFC5545 的 RRULE 认不了法定节假日，所以只能「全唤醒 + 脚本闸门」，别改成按星期硬编码 —— 那样一遇节假日就错。
- 日期归属：**晚上 12 点 = 当天 24:00 = 次日 00:00**，归前一天的日子类型（周日 24:00 是周末班，周一 24:00 是工作日班）。
- 节假日数据：`D:\快捷方式\工作台\dsh\daliy\holidays.json`，源自 NateScarlet/holiday-cn（国务院办公厅公告整理），当前覆盖 2025–2027。每年公告发布后刷新；`daytype` 输出的 `source` 出现「日历未覆盖该年」即在 #291 提醒更新。
## 九、一轮跑完的标准（DoD，2026-11-16 负责人定）

原话：「每次都要跑完完整的任务，不要留下未阻塞的任务。」

每轮结束前逐条自查，任一条不满足就是本轮没跑完：

1. **能合的 PR 全部合了** —— 包括 `branch_behind_main` 的：先 `gh pr update-branch`，同一轮内等 CI 跑绿再合，不推给下一轮。
2. **卡住的 PR 全部退回并留痕** —— PR 评论写清退回到谁、改什么、验收命令；该加 `blocked` 标签就加。
3. **能派的 issue 全部派完** —— 每轮 3 张是单批限额，不是「派不完就下轮」；超出的按优先级列出编号与顺序，别只写「下轮再说」。
4. **验收跑完并清理** —— 隔离 worktree 里 `install/build/tests` 全跑，`worktree remove` 后残留目录（如 `node_modules`）一并删掉。
5. **自己改过的东西当轮就提交** —— 文档、规则、脚本改完直接开 PR，不许躺在工作树里过夜。
6. **台账与回复齐全** —— 每个动作一条台账；回复里有四段回顾、逐 PR 判读卡、动作清单。

「阻塞」只认三种：**等作者改代码、等负责人签名或裁定、等 CI 或外部依赖**。除此之外一律算未阻塞，必须当轮做完。写「下轮继续」必须同时写清阻塞对象与原因，否则视为没跑完。

## 十、汇报纪律（2026-11-16 负责人定）

原话：「每次汇报都要要解释清楚为什么阻塞，哪里需要改变，你的建议是什么。」以及「其他成员会时不时上传 PR 或者 issue 或者需要我处理的事情，不跑任务我就永远看不到，所以最基础的检查还得做。」

### 10.1 每轮都要给简报，不许静默

不管本轮有没有合并、有没有派单，出勤时刻一律先跑基础检查（`hourly-patrol.ps1 -Mode idle`）并给负责人一份简报，三块缺一不可：

1. **新出现 / 有变化** —— 新 PR、新 issue、重新打开的、状态或 CI 或 assignee 变了的、已经收掉的。成员随时会上传东西，静默等于让他永远看不见。
2. **现在压在他身上** —— 派给他的、等他审的、需批准标签、blocked 标签。
3. **待他处理的事** —— 每条按 10.2 三行式写。

状态与上次快照完全一致时，仍要给简报（只写「无动作」不够）；只有在非出勤时刻才允许只回一行「已跳过」。

### 10.2 三行式（缺一行等于没汇报）

他不需要看懂技术细节也能拍板，所以每条卡住的事必须写全：

- **为什么卡住** —— 具体到文件 / 检查项 / 字段 / 编号。反例：「有冲突」。正例：「`docs/decisions.md` 与 main 冲突，main 已用掉 D86，本 PR 也是 D86」。
- **要谁改什么** —— 人名或池 + 具体动作 + 验收命令。反例：「等他改」。正例：「@Tylanbot 改 `0034_*.sql` 并 `merge origin/main`，验收 `pnpm -r build` + `pwsh -File tests/run.ps1`」。
- **我的建议** —— 1 个推荐 + 1 个备选，写清各自代价；需要他签字的直接写「请回 `MERGE-OK: #<n>`」，需要他选口径的写「请回 `ADOPT: #<n>`」。反例：「请负责人决定」。

### 10.3 回复结构

① 上一轮回顾（完成了什么 / 派了什么 / 完成没有 / 接下来做什么）② 基础检查简报 ③ 逐 PR 判读卡 ④ 动作清单（合并、验收、派单、退回、请求裁定各几条）⑤ 待负责人决策（三行式逐条）⑥ 下一轮关注 2–3 条。

## 十一、安全底线：四类安全（2026-11-16 负责人定）

原话：「精神里要补充一点：用户安全，数据安全，产品安全，服务器安全。」

这四条是**第 0 号标尺**，排在 §七 三条（维护成本 / 产品质量 / 性能）之前。任何 PR、任何派单、任何「省事」的理由，只要与下面四条冲突，一律先保安全，且不许拿「以后补」当结论。

### 11.1 用户安全

- **不可越权**：权限只看权限点（`requireScope`），不看职位、不看前端按钮；新增动作必须走契约 `domains.ts` + `docs/decisions.md`。
- **不误伤**：删除、作废、撤销、批量操作必须有边界与二次确认语义；能回滚的优先回滚，不能回滚的要留审计与人工恢复路径。
- **不泄露给不该看的人**：金额、经手人、联系方式等敏感字段按 `view_price` / `view_handler` 脱敏为 `null`，不是 403 也不是 0。
- **登录与会话**：验证码一次性、频控、会话过期、CSRF 同源校验（D59）不许被新写法绕开。

### 11.2 数据安全

- **不丢**：迁移必须前向 only、单文件单事务；已执行迁移不许改（checksum 漂移直接失败）；不可回滚的结构变更必须同 PR 给出备份与回滚步骤。
- **不串**：多租户共享表一律带 `tenant_id` 并有 RLS 兜底（D55）；跨模块只走 `registry.ts` 端口（D70），禁止直读别的模块表。
- **不留死角**：审计全量、只追加、不可改删，业务失败也记，审计失败阻断业务（D51）。
- **不进明文**：密钥、令牌、密码只从环境或密钥存储读，禁止落库、禁止进日志、禁止进仓库；测试用假值。

### 11.3 产品安全

- **状态机不许留死态**：单据每一个状态必须有出边（例 #287 盘点「已驳回」死态就是缺陷）。
- **口径单一真源**：同一件事只有一份定义（契约 / decisions / 迁移三处一致），不许前端一套后端一套。
- **错误可解释**：4xx/409/428 的边界错误必须有明确文案与可定位字段，不许吞异常返回 200。
- **数据与展示一致**：列表、详情、导出、审计里的同一字段口径必须相同（脱敏规则尤其）。

### 11.4 服务器安全

- **最小权限**：数据库账号非 superuser、无 `BYPASSRLS`（D57）；容器内不以 root 跑业务进程。
- **暴露面最小**：只开必要端口；管理端点、调试端点、`dryRun` 之类危险动作默认关闭或需显式授权（D52 ①）。
- **依赖与镜像**：新增依赖要说明用途与体积，锁文件必须提交；不在构建时从网络拉未固定版本的产物。
- **可观测与可恢复**：生产改动要有日志与告警落点；部署必须能回滚（备份 + 迁移前滚方案）。

### 11.5 落到流程上

- **判读卡**：每个 PR 的判读卡必须多写一段「安全影响」——四类逐条判定「涉及 / 不涉及」，涉及就写清怎么保证。
- **派单**：issue 四问之外的第五问固定问「安全影响（四类）」，答案写进 issue，不许留空。
- **验收**：能跑安全相关测试的必须跑（脱敏、权限、审计、RLS、迁移幂等）；跑不了的在报告里写明「未覆盖」与原因。

## 十二、编号与命名（2026-11-16 定，解决反复撞号）

### 12.1 为什么反复撞（经验总结，三次都栽在同一处）

1. **结构性冲突，不是谁疏忽**：迁移号与决策号都是「全局单序列」，N 个并行 PR 各自取「main 最大值 + 1」，N 个 PR 同时开就必然撞。撞号概率与并行度成正比，跟作者水平无关。
2. **发现太晚**：此前没有任何机械校验，撞号只能在合并瞬间由人发现——此时作者已经改完一整套代码、写完 decisions、跑过一轮 CI，代价从「改个文件名」放大成「返工半小时 + 一轮 CI」。
3. **两套序列同时撞**：迁移号（文件名）与决策号（表格行）是两条独立序列，一次冲突往往要改两处，还牵动交叉引用与 OpenAPI 说明。

结论：把「唯一性」交给**时间**，把「顺序」交给**排序规则**，把「发现」交给**CI**，人只负责决策内容。

### 12.2 规则

- **新迁移一律用 14 位时间戳前缀**：`YYYYMMDDHHMMSS_简短说明.sql`（例 `20261116043000_settlement_orders_unsettle.sql`）。时间戳天然唯一，`migrate.ts` 按文件名 `localeCompare` 升序执行，`0033_` 与 `2026…_` 混排时数字前缀永远在前，顺序正确，**不需要改一行代码**。
- **存量 0001–00NN 保持不动**：已应用迁移的 id 已写进 `schema_migrations`，改名等于 checksum 漂移，直接触发失败。
- **决策号（D 号）仍按序**，但**由巡检在 issue 里分配**：开 issue 时就写「占号 D<n>」，PR 标题或描述里写同一号；两人同时领同一个号由巡检协调。号冲突时后领的顺延。
- **一个 PR 只占一个迁移号、一个决策号**：需要多个就拆 PR，别指望「撞了再顺延」。
- **提交前自查**：`node tools/check-numbering.mjs`（默认对比 `origin/main`）；CI 的 `numbering` check 会跑同一份脚本。
- **撞号时的处置**：迁移改名（时间戳不用改内容）；决策号顺延并在 PR 描述注明「因 #<PR> 已用 D<n>，本 PR 顺延为 D<n+1>」。

### 12.3 工具

- `tools/check-numbering.mjs`：扫 `apps/api/migrations/*.sql` 与 `docs/decisions.md`，报告撞号、号不递增、命名不合规，直接打印应取的号；退出码非 0 即失败。本地可带 `--dir` 与 `--base`。
- `.github/workflows/numbering.yml`：PR 上自动跑，check 名 `numbering (迁移号与决策号唯一)`。

### 12.4 为什么不选另外两个方案

- **号段预留（按人分 0100–0199）**：唯一性解决了，但部署顺序变成随机的，`schema_migrations` 的执行序与业务先后脱节，排查成本更高。
- **决策拆成一号一文件（`docs/decisions/D87-xxx.md`）**：能根治表格行冲突，但会打散现有 87 条索引，检索与引用全线重写；等条目超过 200 条再考虑。当前用「巡检单点分配 + CI 校验」成本更低。

## 十三、代码约定（2026-11-16 负责人定）

原话：「代码要简洁易懂高效，留好中文注释，讲清楚功能和原理还有联系，不重复造轮子，时间复杂度低，内存占用低，减少嵌套，删掉冗余代码。」

逐条落到可检查的写法上：

1. **简洁易懂**：一个函数只做一件事，名字说清做什么；超过 40 行先想能不能拆；能用 3 行读懂的不要写成 10 行。
2. **中文注释讲清三件事**：这个文件/函数**做什么**、**为什么这么做（原理）**、**跟谁有关联（依赖的契约、目录、别的脚本）**。禁止写「// 增加 i」这种复述代码的注释。
3. **不重复造轮子**：仓库里已有 `tools/`、`tests/run.ps1`、`.github/workflows/` 的成例，先找再写；能用标准库/现有依赖就不引新依赖，引了要说明用途与体积。
4. **时间复杂度**：能一次遍历不要两层嵌套；查表用 `Map`/`Set` 而不是 `Array.find` 套循环；批量拉数据优先一次拿全（例：一次 `gh pr list --json` 而不是逐 PR 发请求）。
5. **内存占用**：流式处理大文件，不把整份 diff/日志读进数组再筛；大对象用完即弃，不挂在全局。
6. **减少嵌套**：早返回（guard clause）代替多层 `if`；`if/else` 超过两层拆函数；错误路径写在前面，主流程平铺。
7. **删掉冗余代码**：没被引用的函数、变量、`TODO`、注释掉的旧实现，同一 PR 内清掉，不留「以后可能有用」。
8. **脚本类额外要求**：PowerShell 脚本必须带 BOM（5.1 下中文会报 `missing the terminator`），`.mjs`/`.ts` 不带 BOM；行尾统一 LF；改完自己跑一遍正向 + 反向用例再提交。
