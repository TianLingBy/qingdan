### 均摊的实现口径

- 一轮里要派 N 张后端单：按上面 1→5 归类后，同一档内按 **未关闭 issue 数升序** 依次分配，不出现同一个人连吃两张同档单。
- `@Tylanbot` 并行上限 3 单，且**按目录错开**；同一目录已有 open PR 就不派第二张。
- 主线的负载上限：手上未关闭 p0 超过 2 张时，非红线单不再往主线堆，转 `@Tylanbot` 或成员。

## 四、派给 superagent 的写法

1. 由**人类账号**（六人之一，`TianLingBy` 也算）在 issue 里发评论，首行 `@Tylanbot`；用 `@Tylanbot` 自己的账号建单/发评论会被它的来源过滤丢掉。

## 七、红线 PR、冲突、口径分歧怎么处置

**红线 PR 的汇报格式（判读卡，四段缺一不可）**——负责人靠这四段决定合不合，写不出四段就等于没汇报：

1. **改了什么**：逐条列红线文件的改动与增删行数；迁移文件名与编号；`docs/decisions.md` 新增条目原文；`packages/contracts/src/domains.ts` 的域/动作变更。
2. **冲突在哪**：`conflictFiles` 的具体文件；再说清两边各改了什么（`git diff origin/main...origin/<branch> -- <file>`），冲突是「同处改写」还是「各自新增同号迁移」。
3. **与口径是否一致**：逐条对照 `docs/decisions.md`、`AGENTS.md`（权限模型铁律等）、`docs/OWNERSHIP.md`，明确列出「一致项 / 不一致项」。
4. **结论三选一**：可合（写明凭据）/ 对方方案更好 → 先请求负责人同意再改 / 不如口径 → 退回改。

**口径分歧的处置顺序（2026-11-16 负责人口径）**：

- **对方方案优于现口径** → 不许自己改口径，先在 issue/PR 里提「他的做法是 X，比现口径 Y 好在 Z，建议采纳」，**拿到负责人明确同意后**再改 `docs/decisions.md` 与代码。
- **对方方案不如现口径、或验收不达标** → 退回作者改，写清具体改法 + 验收命令；不代写（红线除外，红线本来只有主线能改）。
- **拿不准谁更好** → 把两边摆出来让负责人选，不替他选。

**迁移编号撞车**：多个 PR 抢同一编号时先定合入顺序，后合的把号顺延并在 PR 里注明；同一编号绝不允许存在两个文件。

### 判「谁更好用」的三条标尺（2026-11-16 负责人口径）

原话：「秉承一个精神，开发多花钱，维护更新少花钱。」并补充：「要产品更高的质量与性能。」

判优劣**同时**看这三条，缺一条的判定不成立：

1. **维护与更新成本** —— 少加结构、少加开关、少让人记住额外的约定。但**不许靠借用相邻权限或借用别的域来省**（这是把成本推给以后，不是省）。
2. **产品质量** —— 可回滚、审计留痕、错误态与边界写清、口径单一真源；能补的缺陷当场补（如迁移的 backfill），不留成「下一个人踩」。
3. **性能** —— 查询与渲染代价：有没有 N+1、有没有全表扫、索引跟不跟得上、分页与聚合放在哪一层。

三者冲突时：**先保质量与性能，再谈省维护成本**；三条都不能当作绕开红线或权限铁律的理由（「省事」不是理由，「更快」也不是）。

## 八、巡检出勤节奏与节假日（2026-11-16 负责人定）

| 日子类型 | 出勤时刻 |
|---|---|
| 工作日、调休上班日 | 06:00 / 12:00 / 18:00 / 24:00（即次日 00:00） |
| 周末、法定节假日 | 06:00 / 09:00 / 12:00 / 15:00 / 18:00 / 21:00 / 24:00 |

- 实现方式：调度器**每天**在 06/09/12/15/18/21/00 七个整点唤醒，由 `hourly-patrol.ps1 -Mode daytype` 判当天日子类型与应出勤时刻；`shouldRun=false` 的整点直接跳过（工作日不出勤 09:00 / 15:00 / 21:00）。RFC5545 的 RRULE 认不了法定节假日，所以只能「全唤醒 + 脚本闸门」，别改成按星期硬编码 —— 那样一遇节假日就错。
- 日期归属：**晚上 12 点 = 当天 24:00 = 次日 00:00**，归前一天的日子类型（周日 24:00 是周末班，周一 24:00 是工作日班）。
- 节假日数据：`D:\快捷方式\工作台\dsh\daliy\holidays.json`，源自 NateScarlet/holiday-cn（国务院办公厅公告整理），当前覆盖 2025–2027。每年公告发布后刷新；`daytype` 输出的 `source` 出现「日历未覆盖该年」即在 #291 提醒更新。
## 九、一轮跑完的标准（DoD，2026-11-16 负责人定）

原话：「每次都要跑完完整的任务，不要留下未阻塞的任务。」

每轮结束前逐条自查，任一条不满足就是本轮没跑完：

1. **能合的 PR 全部合了** —— 包括 `branch_behind_main` 的：先 `gh pr update-branch`，同一轮内等 CI 跑绿再合，不推给下一轮。
2. **卡住的 PR 全部退回并留痕** —— PR 评论写清退回到谁、改什么、验收命令；该加 `blocked` 标签就加。
3. **能派的 issue 全部派完** —— 每轮 3 张是单批限额，不是「派不完就下轮」；超出的按优先级列出编号与顺序，别只写「下轮再说」。
4. **验收跑完并清理** —— 隔离 worktree 里 `install/build/tests` 全跑，`worktree remove` 后残留目录（如 `node_modules`）一并删掉。
5. **自己改过的东西当轮就提交** —— 文档、规则、脚本改完直接开 PR，不许躺在工作树里过夜。
6. **台账与回复齐全** —— 每个动作一条台账；回复里有四段回顾、逐 PR 判读卡、动作清单。

「阻塞」只认三种：**等作者改代码、等负责人签名或裁定、等 CI 或外部依赖**。除此之外一律算未阻塞，必须当轮做完。写「下轮继续」必须同时写清阻塞对象与原因，否则视为没跑完。
