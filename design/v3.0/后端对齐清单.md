# 后端对齐清单（新 UI v3.0 能不能合进 repo）

> 目的：这套新 UI 要替换 v0.13 作为实现目标，落地前必须先把「界面上的每个字段、动作、参数」和 `apps/api` 的真身对上。
> 依据：`docs/api/feature-matrix.md`（152 端点 / 24 域，由 spec 生成）、`packages/contracts/src/domains.ts`（域与 11 个动作）、`packages/contracts/openapi.yaml`。
> 结论先说：**新 UI 的东西全部落在现有 152 个端点内**，没有任何一处要求改后端；但有 3 处界面组件对应的端点不存在，已在稿子里改掉或标注，另有 5 处字段要按后端口径写。

## 一、权限词表：已按契约改成 24 域 × 11 动作

| 项 | 之前（我稿子的自造版） | 现在（契约） |
|---|---|---|
| 域 | 24 个自造 key：`purchase_order` `sales_order` `inventory` `apikey` `report` … | **24 个真 key**：`purchase` `processing` `sales` `internal_trade` `settlement` `commission` `customer_return` `supplier_return` `stocktake` `product` `customer` `supplier` `processor` `inventory_qty` `inventory_flow` `employee` `permission` `company` `profit_report` `audit` `api_integration` `payment` `billing` `workbench` |
| 动作 | 自造 8 个：`read create update delete ship approve export read_all` | **11 个真动作**：`read` `read_all` `create` `update` `approve` `ship` `delete` `merge` `view_price` `view_handler` `export`（`domains.ts:56-68`） |
| 矩阵规模 | 24 × 8 = 192 格 | **24 × 11 = 264 格**（页面已改） |

## 三、三处「界面上有、后端没有」——已改掉

| 位置 | 之前 | 现在 |
|---|---|---|
| 盘点页 | 「新建盘点单」+「编辑」+「删除」按钮 | 拆成 **「盘盈单」（increases）+「盘亏单」（decreases）**；**删掉编辑与删除**（后端两个动作都没有）；驳回改成**必填原因**弹层 |
| API 与集成 | 撤销后可「重发」 | 改成「**新建**」——后端只有 `POST /api-tokens`（创建）/ `GET`（列表）/ `DELETE`（撤销），**没有「重发一枚」的端点**；新 token 只能重新创建 |
| 操作日志 | 表头有「导出」 | **删掉** —— `audit` 域只有 `GET /audit-logs` 一个端点，没有导出 |

## 四、五处字段口径：按后端改法写（不是后端要改）

| 位置 | 后端真身 | 稿子的处理 |
|---|---|---|
| 库存「低库存预警」 | `GET /inventory/alerts`：可用量 < 近 30 天日均出库 × 7 ×（1+提前量），**服务端算**（D104） | 列名从「安全库存」改成**「低库存预警」**，页头写明 D104 口径；演示数据用等价阈值 |
| 库存「库龄」 | 批次有 `createdAt`（`GET /inventory/batches`），**没有现成的库龄字段** | 保留列，口径写「按批次 createdAt 到今天」；如后端愿加 `ageDays` 更好，但不阻塞 |
| 金额列 | 无 `view_price` 时后端把金额置 `null`（不是 0） | 全稿用「—」占位，不做 `0` 兜底 ✓ |
| 分页 | 列表查询参数是 **`page` + `pageSize`** | 分页控件按这两个参数接线；页脚「共 N 条 · 合计」取全量筛选结果 |
| 打印客户联 | `GET /sales-orders/{id}/print` 回 **HTML 文本**（无 PDF） | 稿子就是浏览器打印 HTML，一致 ✓ |

## 五、一处要后端补、否则页面只能当流程示意

**入企页（`/login` 的「邀请码加入企业」）**：`/auth/*` 只有 `code` / `login` / `logout` / `me` 四个端点，**没有邀请码/加入企业端点**。

- 现状处理：稿子里该页保留（#435 要求画），页面底部明确写「后端暂缺此端点，落地前需补，或改为管理员建号 + 手机号登录」。
- 若要真做，最小后端缺口是一个「校验邀请码 → 绑定员工到公司」的端点；**这属于新增后端能力，超出「后端已冻结」的前提**，需要负责人拍板。

## 六、另外三条硬约束（界面侧遵守即可，不用后端改）

1. **`If-Match`**：写端点带乐观锁，前端从上次 GET 的响应头取 etag（`update/ship/complete/confirm/approve/cancel` 全套都在表里标了「是」）。
2. **不许画**：销售单「审批」（只有 `ship`/`complete`/`cancel`，签收就是 `complete`）、物理删除、批量操作、附件上传、打印 PDF、除 `profit_report`/`commission` 外的统计图。
3. **`money` / 数量**：金额与数量一律 decimal 字符串，前端不参与运算（表里 `totalAmount` 可能为 `null`）。

## 七、结论

- **新 UI 可以直接作为实现目标**：所有页面、按钮、状态都能映射到现有 152 个端点上；四态用 `data-state`（`filled/empty/loading/error`），类名与 `app-v013.css` 对齐。
- **唯一需要后端新增的能力是「邀请码加入企业」**，其余全是前端照契约接线。
- 本清单里「已改掉」的四处（盘点编辑/删除、密钥重发、日志导出、域与动作词表）都已改进 `design/v3.0/index.html`，可对照验证。
